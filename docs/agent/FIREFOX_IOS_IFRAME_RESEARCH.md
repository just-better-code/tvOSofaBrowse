# Дослідження iframe у Firefox для iOS

Дата дослідження: 2026-10-01. Переглянута ревізія Firefox: [`371a1b51c54645dbcbd7ad41d1479c7a9e5850f8`](https://github.com/mozilla-mobile/firefox-ios/tree/371a1b51c54645dbcbd7ad41d1479c7a9e5850f8). Локальний скорочений зріз: `.references/firefox-ios-research/`. Це аналіз вихідного коду, а не перевірка поведінки двох браузерів. Обидва застосунки використовують WebKit, але Firefox отримує дотики всередині сторінки, а наш застосунок перетворює дії пульта й курсора на події сторінки.

## Головний висновок

Firefox не отримує необмеженого доступу до DOM стороннього iframe з батьківської сторінки. Він встановлює потрібні `WKUserScript` **усередині кожного фрейму**: скрипт читає власний документ і надсилає повідомлення нативному коду. Коли відповідь треба виконати в конкретному фреймі, Firefox зберігає `WKScriptMessage.frameInfo` і запускає JavaScript саме там. Навігацію основної сторінки він відрізняє від навігації вкладених фреймів. У переглянутих компонентах Firefox немає готового універсального механізму кліків пультом або керування довільними відеоплеєрами.

## Критерій готовності від користувача

Мета — дати користувачеві доступ до **елементів керування, які надає сам плеєр сайту**, і забезпечити їхню задуману дію так, як у звичайному браузері. Це стосується не лише запуску потоку або нашої окремої команди Play/Pause. Для підтримуваного WebKit плеєра потрібно перевірити, що курсор може дістатися видимих кнопок, меню та шкали часу; Center активує саме обраний елемент; hover, фокус, відкриття меню, вибір пункту, перемотування й fullscreen працюють за правилами цього плеєра; після виходу з fullscreen керування повертається. Вкладений або сторонній iframe не повинен ламати ці дії чи змінювати історію вкладки. Стан вибору має зберігатися механізмами самого сайту.

Критерій підтверджується спостереженням взаємодій на різних реалізаціях плеєрів у симуляторі; за потреби користувач підтверджує поведінку на своєму Apple TV після окремого дозволу на роботу з пристроєм. Сам факт доставки `postMessage`, виклику `video.play()` або запуску відео не означає виконання цього критерію. Якщо певну дію WebKit чи сайт принципово не дозволяє, потрібен конкретний опис цієї межі, а не твердження про повну підтримку.

Детальний локальний [план реалізації](plans/iframe-player-controls.md) починається з перевірки справжньої дії користувача в цільовому iframe. [WebKit пояснює](https://webkit.org/blog/13862/the-user-activation-api/), що активація з батьківської сторінки не переходить автоматично до стороннього фрейму. [Реальний випадок у WebKit](https://commits.webkit.org/313743@main) показує, що `postMessage` до YouTube iframe не переніс user gesture і відтворення не почалося. [Apple зазначає](https://developer.apple.com/design/human-interface-guidelines/web-views), що web views не підтримуються у tvOS як звичайна публічна можливість, тому поведінку доступного runtime треба перевіряти окремо. Ще одна конкретна гіпотеза: `ShadowRoot.elementFromPoint()` приймає координати viewport ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/ShadowRoot/elementFromPoint)), а наш поточний код віднімає координати host; це потребує цільової перевірки.

## Як Firefox працює з фреймами

1. [Менеджер скриптів](https://github.com/mozilla-mobile/firefox-ios/blob/371a1b51c54645dbcbd7ad41d1479c7a9e5850f8/firefox-ios/Client/Frontend/TabContentsScripts/UserScriptManager.swift) завантажує окремі збірки для `AllFrames` і `MainFrame`, на початку або наприкінці завантаження документа. Це видно також у [структурі збірки](https://github.com/mozilla-mobile/firefox-ios/blob/371a1b51c54645dbcbd7ad41d1479c7a9e5850f8/firefox-ios/README.md) та [конфігурації webpack](https://github.com/mozilla-mobile/firefox-ios/blob/371a1b51c54645dbcbd7ad41d1479c7a9e5850f8/webpack.config.js). Параметр `forMainFrameOnly: false` запускає скрипт у всіх фреймах, зокрема сторонніх, але не надає батьківській сторінці доступу до їхнього DOM ([Apple](https://developer.apple.com/documentation/webkit/wkuserscript/isformainframeonly?language=objc)).
2. Firefox розділяє призначення скриптів і простори JavaScript. Звичайні помічники працюють у просторі застосунку; суміснісні виправлення працюють у просторі сторінки, бо мають підміняти видимі їй API. Для нічного режиму є окремий іменований простір. [Розширення WebKit](https://github.com/mozilla-mobile/firefox-ios/blob/371a1b51c54645dbcbd7ad41d1479c7a9e5850f8/BrowserKit/Sources/Shared/Extensions/WKWebViewExtensions.swift) реєструє обробники повідомлень у вибраному просторі. Ізоляція розділяє змінні JavaScript; зміни DOM залишаються спільними ([Apple](https://developer.apple.com/documentation/webkit/wkuserscript/init%28source%3Ainjectiontime%3Aformainframeonly%3Ain%3A%29)). Вона не обходить правило одного джерела.
3. [Скрипт фокусу](https://github.com/mozilla-mobile/firefox-ios/blob/371a1b51c54645dbcbd7ad41d1479c7a9e5850f8/firefox-ios/Client/Frontend/UserContent/UserScripts/AllFrames/AtDocumentEnd/FocusHelper.js) слухає focus/blur у власному документі й повідомляє [стан вкладки](https://github.com/mozilla-mobile/firefox-ios/blob/371a1b51c54645dbcbd7ad41d1479c7a9e5850f8/firefox-ios/Client/Frontend/TabContentsScripts/FocusHelper.swift). [Скрипт контекстного меню](https://github.com/mozilla-mobile/firefox-ios/blob/371a1b51c54645dbcbd7ad41d1479c7a9e5850f8/firefox-ios/Client/Frontend/UserContent/UserScripts/AllFrames/AtDocumentStart/ContextMenu.js) обробляє дотик чи натискання миші в самому фреймі та передає посилання або зображення. Батьківській сторінці не потрібно обходити DOM дочірнього фрейму.
4. [Скрипт форм входу](https://github.com/mozilla-mobile/firefox-ios/blob/371a1b51c54645dbcbd7ad41d1479c7a9e5850f8/firefox-ios/Client/Frontend/UserContent/UserScripts/AllFrames/AtDocumentStart/LoginsHelper.js) надсилає повідомлення з фрейму, якому належить форма. [Нативний обробник](https://github.com/mozilla-mobile/firefox-ios/blob/371a1b51c54645dbcbd7ad41d1479c7a9e5850f8/firefox-ios/Client/Frontend/TabContentsScripts/LoginsHelper.swift) читає `message.frameInfo.request.url`, `securityOrigin.host` та `isMainFrame`. Запити даних для входу він приймає лише з основного фрейму, оскільки відповідь адресована саме йому. Для генерації пароля й автозаповнення Firefox зберігає фрейм та виконує JavaScript через [оцінювач скриптів](https://github.com/mozilla-mobile/firefox-ios/blob/371a1b51c54645dbcbd7ad41d1479c7a9e5850f8/firefox-ios/Client/Frontend/PasswordGenerator/PasswordGeneratorScriptEvaluator.swift) і [помічник автозаповнення](https://github.com/mozilla-mobile/firefox-ios/blob/371a1b51c54645dbcbd7ad41d1479c7a9e5850f8/firefox-ios/Client/Frontend/TabContentsScripts/FormAutofillHelper/FormAutofillHelper.swift). `WKScriptMessage.frameInfo` визначає фрейм відправника ([Apple](https://developer.apple.com/documentation/webkit/wkscriptmessage/frameinfo)); адресне виконання є публічним API WKWebView, який повертає помилку, якщо фрейм уже зник ([Apple](https://developer.apple.com/documentation/webkit/wkwebview/callasyncjavascript%3Aarguments%3Ainframe%3Aincontentworld%3Acompletionhandler%3A?language=objc)).
5. Firefox відділяє навігацію фрейму від навігації вкладки. [Обробник навігації](https://github.com/mozilla-mobile/firefox-ios/blob/371a1b51c54645dbcbd7ad41d1479c7a9e5850f8/firefox-ios/Client/Frontend/Browser/WebView/WebViewNavigationHandler.swift) не застосовує обмеження верхнього рівня для `data:` у вкладених фреймах. [Делегат браузера](https://github.com/mozilla-mobile/firefox-ios/blob/371a1b51c54645dbcbd7ad41d1479c7a9e5850f8/firefox-ios/Client/Frontend/Browser/BrowserViewController/Extensions/BrowserViewController%2BWebViewDelegates.swift) використовує `targetFrame?.isMainFrame` та `navigationResponse.isForMainFrame` для вибору User Agent і обробки документа. `targetFrame == nil` означає ціль у новому вікні, а не звичайне завантаження основного фрейму ([Apple](https://developer.apple.com/documentation/webkit/wknavigationaction/targetframe?language=objc)).
6. Нинішній [fullscreen-скрипт](https://github.com/mozilla-mobile/firefox-ios/blob/371a1b51c54645dbcbd7ad41d1479c7a9e5850f8/firefox-ios/Client/Frontend/UserContent/UserScripts/AllFrames/WebcompatAtDocumentStart/FullscreenHelper.js) Firefox працює умовно: додає запасний шлях, коли нативний fullscreen недоступний із десктопним User Agent, та примусово вмикає inline autoplay для щойно створених відео у десктопному режимі. У Mozilla є [відкрите питання](https://github.com/mozilla-mobile/firefox-ios/issues/33992) щодо fullscreen елементів, які не є відео, і регресій старих підмін. Отже, цей код не доводить підтримку довільного fullscreen-плеєра в iframe.

## Пропозиції для подальшої реалізації

1. **Протокол взаємодії всередині фрейму.** Нехай скрипт кожного фрейму відповідає на вузькі запити: тип елемента під курсором, стан фокусу й редагування, видиме відео. Команди курсора адресувати конкретному фрейму. Прив'язати відповіді до вкладки, ID запиту й покоління навігації, щоб запізніла відповідь не діяла на новій сторінці. Дослідити `WKScriptMessage.frameInfo` на tvOS; залишити нинішній `postMessage` як запасний шлях. Перші складні випадки — вкладений сторонній iframe та iframe у відкритому Shadow DOM.
2. **Єдина модель координат і визначення цілі.** Централізувати перехід між координатами tvOS view, viewport сторінки, областю вмісту iframe, прокруткою, CSS zoom, трансформаціями та масштабом дисплея. Поточний міст використовує `getBoundingClientRect()` і `offsetWidth/offsetHeight`; цього може не вистачити для поворотів, нахилу, обрізання та вкладених трансформацій. Такі випадки треба дослідити окремо, а не вважати, що лінійний масштаб їх покриває.
3. **Зберегти поведінку елементів сайту.** Center має активувати елемент під курсором через той шлях вводу, який WebKit і сайт сприймають як звичайну дію користувача. Не підміняти натискання кнопок плеєра прямими викликами `video.play()`, зміною `currentTime` чи власним fullscreen, коли це обходить логіку сайту. Play/Pause і Left/Right спрямовувати до активного або явно обраного плеєра лише відповідно до його доступного способу керування. Додати підтвердження виконання чи помилки: сама відправка повідомлення ще не означає успіх. Для суто canvas-плеєрів або закритих API не обіцяти універсального керування.
   Окремо перевірити плеєри, яким потрібна справжня дія користувача: події, створені через JavaScript, не мають `isTrusted` і не створюють user activation ([MDN](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/User_activation)); WebKit може вимагати таку дію для відтворення зі звуком ([WebKit](https://webkit.org/blog/6784/new-video-policies-for-ios/)). Доставка синтетичного кліку сама по собі не гарантує старту відео.
4. **Зменшити підміну fullscreen.** Перед заміною API перевіряти підтримку нативного fullscreen. Синхронізувати стан сторінки й iframe після входу, виходу, навігації та видалення фрейму. Врахувати відомі регресії Firefox для елементів, які не є відео, та десктопного User Agent.
5. **Перевірити навігацію й діагностику за фреймами.** Завантаження iframe не повинно змінювати історію, URL, назву вкладки чи обробку нового вікна; `targetFrame == nil` розглядати окремо. Дослідити встановлення скрипта діагностики лише при ввімкненій діагностиці: зараз він перехоплює звернення до storage й запускає таймер, навіть коли нативне журналювання вимкнено. У діагностичних матеріалах не зберігати ключі storage чи особисті дані сторінки.

## Що треба перевірити перед вибором рішення

Коли буде запит на перевірку, підготувати сценарії для однакових і різних джерел, вкладених iframe, відкритого й закритого Shadow DOM, sandboxed iframe, масштабованих/трансформованих/обрізаних фреймів, фокусу поля, `window.open` і `target=_blank`, нативного відео, власного iframe-плеєра та входу/виходу з fullscreen. На симуляторі перевірити, що саме доступно через `WKFrameInfo`, адресне виконання JavaScript і content worlds у підтримуваній версії tvOS. Сама компіляція або запуск не підтверджують роботу кліку, фокусу, seek чи fullscreen. Робота з фізичним Apple TV потребує окремого дозволу згідно з `AGENTS.md`.
